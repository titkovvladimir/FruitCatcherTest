# Поймай фрукты

**Играть: https://titkovvladimir.github.io/FruitCatcherTest/**

Корзина внизу экрана, падающие сверху фрукты, ограниченное время и запас
жизней.
Пойманный фрукт приносит очки, пойманный мухомор отнимает жизнь.

Тестовое задание: Cocos Creator 3.8, TypeScript со строгими настройками.

**Что уже играется:** игра открывается выбором из трёх сложностей — они
отличаются длиной раунда, запасом жизней, густотой потока и темпом падения.
В раунде предметы пяти типов падают тремя траекториями, корзина ходит за
курсором, пойманное приносит очки, мухомор отнимает жизнь. На экране — счёт,
обратный отсчёт и запас жизней; раунд ставится на паузу кнопкой и сам встаёт,
если свернуть вкладку. Конец раунда по времени или по жизням показывает панель
итога, откуда можно сыграть тот же уровень ещё раз или вернуться к выбору.
Лучший счёт запоминается по каждой сложности отдельно и виден и на панели итога,
и на кнопках выбора.

Числа сложностей — заготовка: отдельной настройкой баланса они ещё не проходили.
Порядок дальнейших работ — в [плане](docs/PLAN.md).

## Как собрать и запустить

Нужен Cocos Creator 3.8.8.

**Из редактора.** Открыть проект, открыть `assets/scenes/Game.scene`, нажать
превью.

**Из командной строки.** Сборка идёт без редактора, одной командой:

```bash
"<путь>/CocosCreator.exe" --project "<путь к проекту>" --build "platform=web-mobile;debug=false"
```

Готовая игра ложится в `build/web-mobile`. Открывать её надо с локального
сервера, а не двойным щелчком по `index.html`: движок дотягивает ассеты
запросами, и по `file://` они не проходят.

```bash
python -m http.server 8123 --directory build/web-mobile
```

**Проверки.** Понадобится один раз поставить зависимости разработки — в проекте
их ровно одна, компилятор TypeScript:

```bash
npm install
```

Дальше обе проверки одной командой:

```bash
npm run check
```

Их две, и каждая закрывает то, о чём сборка молчит.

`npm run typecheck` — сборка Cocos код транспилирует, но на ошибках типов не
останавливается, поэтому `strict` проверяется отдельным вызовом. Флаг
`--skipLibCheck` в нём обязателен: собственные `.d.ts` движка под `strict` не
проходят, и без флага его ошибки топят наши.

`npm run check-scene` — ссылка на свой компонент внутри сцены записывается
идентификатором класса, выведенным из uuid скрипта. Ошибка в нём молчит: сборка
проходит с нулевым кодом возврата, а компонент из собранной сцены исчезает.
Скрипт выводит те же идентификаторы из скриптов проекта и сверяет со сценами.

`npm run check-links` — документы здесь часть сдаваемого и ссылаются друг на
друга. Переехавший файл ломает ссылку молча, и находит её читатель. Примеры
формата внутри обратных кавычек и блоков кода из проверки исключены: они
выглядят как ссылки, но ведут в никуда нарочно.

**Публикация.** Играбельная сборка лежит в ветке `gh-pages`: содержимое
`build/web-mobile` в корне. Перед тем как её туда класть:

```bash
npm run pages
```

Команду надо выполнить **до** переключения на ветку сборки: `package.json`
живёт только в основной ветке, и на `gh-pages` её просто нечем запустить.

Команда кладёт в собранную папку `.nojekyll`. Без него Pages прогоняет
содержимое через Jekyll, а тот не отдаёт файлы, начинающиеся с подчёркивания, —
то есть сам движок. Страница получается серая, и по ней не догадаться, в чём
дело. Файл приходится ставить каждый раз: сборка стирает папку целиком.

## Структура проекта

Дерево растёт вместе с игрой: код появляется по шагам [плана](docs/PLAN.md), и
папки заводятся тогда, когда в них есть что положить.

```
assets/configs/    таблицы данных: типы предметов, уровень, корзина
assets/scenes/     сцена игры
assets/scripts/    код игры
assets/textures/   картинки из выданного архива
build-templates/   что подменяется в собранной игре: страница и иконка
docs/              план, решения, архитектура, бэклог
settings/          настройки проекта Cocos
tools/             служебные скрипты: проверки репозитория
```

Раскладка `assets/scripts` по слоям, дерево сцены и владельцы событий расписаны
в [ARCHITECTURE.md](docs/ARCHITECTURE.md) — здесь они не дублируются, чтобы не
разъезжались.

## Подход

### Декомпозиция работ

Один шаг плана — один коммит. История коммитов здесь такой же результат, как
код: по ней должно читаться, в каком порядке росла игра, а не «когда автор
решил сохраниться».

Отсюда два правила. **Каждый шаг после того, как игра впервые запускается,
добавляет ровно одно наблюдаемое** — падение, движение корзины, ловлю, счёт;
после любого из них игра по-прежнему запускается, и видно, что именно
прибавилось. И **каждый слой заводится там, где у него появляется первый
потребитель**: пул приходит вместе с предметами, которые он пулит, хранилище —
вместе с рекордами, которые оно пишет. Слой, заведённый заранее, стоит без
единого вызова и читается как каркас ради каркаса.

### Первый компонент на узле — раньше правил игры

Движок здесь осваивается по ходу работы, и это меняет порядок. Первый
компонент, читающий живой узел сцены, стоит вторым шагом плана — до правил
раунда, до стратегий падения, до разбора ловли. Он проверяет разом всё, на чём
можно споткнуться молча: компилируется ли TypeScript под Cocos, цепляется ли
компонент к узлу, какие размеры и координаты на самом деле отдаёт
`UITransform`.

Порядок «сначала все правила, потом первый запуск» выглядит опрятнее, но в нём
шесть файлов пишутся против непроверенных допущений о движке, а выясняется это
на седьмом.

### Слои и одна проверяемая граница

Шесть папок верхнего уровня: `utils` — технический код без домена, `platform` —
внешний мир (хранилище, источник конфигов), `core` — правила раунда, `meta` —
всё вокруг раунда, `ui` — показ, `roots` — сборка.

Важно здесь не число папок, а одно правило, которое можно проверить, а не
пообещать: **в `core/logic` и `meta/logic` нет ни одного импорта из `cc`**. Слой,
который физически не видит движок, невозможно случайно завязать на размер узла
или позицию спрайта — а значит правила игры заводятся в обычном тесте, без сцены
и без редактора. Остальное деление вторично и обсуждаемо; это — нет.

Из того же правила растёт второе: чисел сцены в коде не бывает. Границы поля,
ширина проёма корзины, размеры предметов читаются из `UITransform` в рантайме.
Растянул поле мышью — код подстроился, потому что исходного размера он и не знал.

И третье: `core` не знает про `meta` ничего. Раунд поднимает свой итог и на этом
заканчивается, а кто запишет из него рекорд — не его забота. Такие архитектуры
протекают первым делом именно здесь, через «ну тут раунду надо обновить рекорд».

### События: сигнал принадлежит владельцу

Вместо движкового `EventTarget` — свой `Signal<T>` на полтора десятка строк.
Причина простая: у `EventTarget` ключи строковые, а нагрузка `any`, и при
`strict: true` от типов не остаётся ничего — опечатка в имени события ловится не
компилятором, а руками на отладке.

Общей шины нет. Сигнал объявляется полем у того, кто владеет состоянием:
`levelSession.scoreChanged`. Видно, чьё это событие, и переименование ловит
компилятор. Наружу сигнал отдаётся как `Subscribable`, где нет `emit`, — поднять
чужое событие нельзя; это то, что в C# делает слово `event`.

Отписки не оставлены на внимательность: подписка идёт через сумку, а сумка
чистится в `onDisable` и `onDestroy`. Поверх неё сторож — в отладочной сборке
`Signal` предупреждает, когда подписчиков на одном сигнале становится
подозрительно много. Он нужен из-за пула: узел не уничтожается, а выключается, и
подписка, сделанная однажды в `onLoad`, тихо удваивалась бы при каждой выдаче.
Игра от этого не падает, она просто через минуту начинает жевать кадры, и найти
причину глазами почти нельзя.

### Движение и ловля без физики

Физического движка в игре нет, хотя соблазн был: Box2D бесплатно дал бы и отскок
фрукта от бортика, и его погружение в корзину.

Против него само задание. Траектории в нём названы авторскими: равномерная,
зигзагом, с ускорением. Под такие гравитацию пришлось бы выключить и каждый кадр
писать телу скорость самим — то есть на обязательной части физика не считает
ничего, зато забирает предсказуемость. Динамические тела в паре с пулом объектов
дают плавающие баги, а половина поведения переезжает из кода в настройки
инспектора, которых в репозитории не видно.

Вместо этого позиция падающего предмета — чистая функция от времени жизни:
`offsetAt(age)` возвращает смещение от точки появления. Не приращение за кадр:
так нет накопления ошибки, путь одинаков на тридцати и на ста сорока кадрах, а
стратегии проверяются без движка вовсе.

Ловля — не наложение прямоугольников, а пересечение отрезка `prevY → curY` с
линией проёма корзины. Быстрый фрукт не проскочит сквозь неё между кадрами:
проверяется путь, а не точка. Ровно за этим обычно и зовут физику.

Сочность делается дешевле: пойманное становится дочерним узлом корзины и потому
едет вместе с ней, доезжая внутрь твином; отскок от бортика — твин в сторону;
погружение — порядок отрисовки между задней и передней стенкой корзины.

### Мета: три сложности вместо витрины

Мета здесь не папка на вырост: у неё три кнопки сложности, три конфига уровня и
рекорд по каждой из них, переживающий перезапуск.

Витрину прошлых результатов рассматривали и отклонили. Она обосновывалась тем,
что без неё слой меты пуст, — то есть архитектурой, а не игроком, и в задании
такого экрана нет. Выбор сложности делает то же самое честнее: у меты появляется
собственное сохраняемое состояние, а три конфига заодно показывают, что баланс
живёт в данных, а не в коде.

### Конфиг описывается один раз

Содержимое конфигов не проверяет никто, кроме нашего кода: импорт JSON смотрит
только на синтаксис, а `strict` — на типы, которых в рантайме не существует.
Число 999 в поле, ждущем от единицы до десяти, доедет до игры целым.

Проверка писалась в два подхода. Сначала руками, по тем полям, что реально есть:
пока схема меняется каждый час, описание переписывалось бы вместе с ней. Когда
схема устоялась — на играбельном срезе, — ручные проверки заменило описание
формы данных, из которого получаются сразу и проверка в рантайме, и тип для
компилятора:

```ts
const BASKET = object({
    speed: number({ min: 1 }),
    snapDistance: number({ min: 0, max: 50 }),
});

export type BasketConfig = Infer<typeof BASKET>;
```

Второго списка полей, который можно забыть поправить, в проекте нет — а он
единственный источник тихого расхождения между типом и проверкой.

Заодно описание строже прежних проверок: поле, которого в нём нет, — ошибка.
Это ловит настройку, которую никто не читает: выставленное в json `bonusScore`
раньше проходило молча и выглядело работающим. Строгость при этом свойство
источника, а не схемы: для своего файла лишнее поле ошибка, а для данных извне —
удалённого конфига или сохранения — та же строгость сделала бы нерабочими все
ранее опубликованные сборки, стоило бы добавить поле на сервере. Терпимый режим
появится вместе с первым таким источником.

### Бюджет цепочки

Читаемость легко объявить и невозможно проверить, поэтому у неё здесь есть
число. Тот, кто открывает чужой проект, идёт не по дереву папок, а по одной
цепочке: откуда взялось вот это на экране. Предел — не больше трёх файлов вниз
от факта до сборщика и трёх вверх от сборщика до пикселя.

«Фрукт пойман → очки и всплывающее число» в него укладывается: `FallingItem`,
`CatchResolver`, `FallingItemConfig`, сборщик, `LevelSession`, `ScoreLabel`.
«Время вышло → панель итога с рекордом» выходит за предел: пять звеньев, и вся
лишняя длина набегает на участке меты. Это прямая цена границы `core` / `meta`;
она принята сознательно и сосредоточена в одном файле, а не размазана по коду.

## Где сознательно упростили

* **физики нет** — см. выше. Кучи фруктов, толкающихся в корзине, из этого
  решения не получится;
* **пул узлов взят по привычке боевого проекта, а не по замеру.** На десятке
  объектов в кадре он не окупается измеримо, и честнее сказать это, чем выдать
  его за оптимизацию. Пул при этом движковый: свой пришлось бы положить в
  `utils`, а этому слою запрещено знать про движок;
* **у падающего предмета нет префаба** — узел собирается кодом. Настраивать в
  префабе нечего: размер и картинка приходят из таблицы типов. Префаб появится
  вместе с украшением — тенью, вспышкой при поимке, — то есть когда в нём будет
  что держать;
* **экрана ошибки нет.** Битый конфиг игра встречает молча: разбор падает в
  консоль, а на экране остаётся исправная на вид игра без единого фрукта.
  Игроку сообщение о поле `spawn.maxInterval` ничего не даёт, а ловится такое
  до релиза;
* **счёт, таймер, жизни и знаки кнопки паузы — системный шрифт**, а не
  картинки. Сердца среди выданных изображений нет, и рисовать своё ради
  тестового не стали; цена — вид символов зависит от шрифта устройства, на
  части телефонов пустое сердце может отрисоваться иначе, чем на десктопе;
* **затемнение и подложка кнопки — встроенный белый спрайт движка**,
  покрашенный цветом: своих картинок под них нет;
* **текстуры лежат как выданы:** фон 2.2 МБ, фрукты под 700×900 на экранный
  размер в разы меньше. Даунскейл и атлас идут отдельным шагом, с замером до и
  после — иначе это разговор, а не оптимизация;
* **сортировки и витрины результатов нет** — только рекорд по сложности;
* **в кадровом коде есть аллокации.** Траектория возвращает смещение объектом,
  предмет и корзина так же отдают своё положение разбору ловли — это около
  тысячи коротких объектов в секунду на десятке предметов. Выбрано ради
  читаемости: обратная сторона — выходные параметры и мутируемые структуры во
  всех подписях. На этом числе предметов цена не измеряется; вырастет число —
  меняется первым делом.

Что доделал бы в реальном проекте: правило линтера на подписки в дополнение к
сумке и сторожу; расширение редактора Cocos, правящее конфиги баланса в UI
вместо текста; удалённый источник конфигов — интерфейс под него уже есть, а
сегодняшняя реализация читает локальный `JsonAsset`. Полный список открытого —
в [BACKLOG.md](docs/BACKLOG.md).

## Инструменты

Cocos Creator 3.8.8, TypeScript со строгими настройками, WebStorm.

Работа идёт в связке с Claude Code. Код и документы пишутся им, решения проходят
через разбор: предложение отклоняется, если под ним нет причины, которую можно
произнести вслух. Так физика была предложена и отменена после сверки с заданием,
витрина результатов — заменена выбором сложности, а правило отписок уточнилось,
когда выяснилось, что для объектов из пула пара `onLoad` / `onDestroy` не
работает.

Подборка ключевых промптов и разбор того, как результат правился под свой
подход, — в [PROMPTS.md](PROMPTS.md).
